# Multi-Agent-Pro 面试含金量提升计划

## 结论

`multi-agent-pro` 作为 Agent 开发工程师面试项目是够用的，而且比普通 Agent demo 深一层。它已经覆盖主 Agent + 子 Agent 编排、工具调用、FastAPI 异步任务、WebSocket 进度、SQL 只读安全、文件读写、ContextVar 会话隔离和结构化日志。

如果目标是冲中高级 Agent 工程师，目前还差几块更能体现工程深度的能力：可评测、可恢复、可观测、真 RAG、工具安全闭环和生产级任务调度。现在更像“完整 MVP + 很好的面试讲稿”，补完下面几项后会更像“企业级 Agent 系统”。

## 当前亮点

- Agent 架构完整：`agent/mainagent/runner.py` 用 DeepAgents/LangGraph 组装主 Agent 和 5 个子 Agent，职责拆分清晰。
- 工程闭环不错：`api/server.py` 提供任务提交、上传、下载、状态查询和 WebSocket。
- 有安全意识：`tools/sql_validator.py` 限制只读 SQL，文件工具也做了扩展名限制。
- 有面试叙事材料：`docs/面试复习深挖讲稿.md` 已经能支撑 1 分钟、3 分钟、8 分钟展开。
- 基础自检能跑通：prompt/config/context、SQL validator、5 个子 Agent 装配都可以验证。

## 优先改进方向

### 1. 补 Agent Eval 体系

- 增加 10-20 条固定任务集：查 Sprint 缺陷、生成周报、上传文件复盘、RAG 规范核对。
- 每条任务定义期望工具调用顺序、关键事实、输出结构和幻觉检查。
- 增加 `evals/` 或 `tests/evals/`，面试时可以说明“不是只看能不能跑，而是评测工具选择、事实一致性和报告质量”。

### 2. 把内存态改成可恢复任务系统

- `TaskStore` 从内存迁到 SQLite/Postgres/Redis。
- `InMemorySaver` 改成 Redis/Postgres checkpoint。
- 增加任务取消、超时、失败重试、重启后恢复。
- 这是最能体现后端工程能力的一项。

### 3. 补真 RAGFlow 或本地 RAG 闭环

- 当前 RAGFlow 更像 stub，占位价值大于实战价值。
- 加入规范文档入库、检索、引用来源、答案可溯源。
- 输出报告中标注“来自数据库 / 上传文件 / RAG / 搜索”的证据来源。

### 4. 加强工具安全边界

- 文件读写必须强制限制在当前 `session_dir` 或 `output` 下，不能只靠 prompt 约束。
- 上传文件名做 `Path(filename).name` 清洗，防止路径穿越。
- SQL 校验升级为 parser-based 或只允许白名单视图查询，并加查询超时和行数限制。

### 5. 强化可观测性

- WebSocket 事件持久化，前端重连后能补发历史事件。
- 日志增加 trace span：主 Agent、子 Agent、工具调用、耗时、token、错误分类。
- 面试时可以展示一次任务从 API 到工具再到报告的完整 trace。

## 面试展示策略

- 不要只说“我做了五个 Agent”，要主讲三个点：为什么拆 Agent、如何保证执行顺序、如何防止 Agent 乱查乱写。
- Demo 最好准备一条端到端任务：上传测试报告 -> 查 MySQL -> 搜索行业实践 -> 分析 -> 生成 Markdown/PDF -> WebSocket 展示进度。
- 主动承认 MVP 取舍：内存任务、单 WebSocket 连接、RAGFlow stub。然后立刻讲可升级方案，这会显得更真实、更工程化。

## 后续优化空间

- 增加 `README` 中的面试演示入口，提供一条固定 demo 命令。
- 增加架构图和一次完整 trace 示例，让面试官能快速理解系统链路。
- 把“当前能力 / MVP 取舍 / 生产化升级”整理成一页表格，方便面试时快速讲清楚边界。

## 假设

- 面试目标是 Agent 开发 / AI 应用后端岗位，而不是纯算法研究岗。
- 前端只作为联调展示，不作为主要评分点。
- 最优先补强方向是企业级 Agent 落地能力，不是继续堆更多子 Agent。
