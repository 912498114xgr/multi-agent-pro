## 1. 一句话：这次迭代要解决什么

普通 Agent demo 常见两种极端：

1. 工具一抛异常 → **整单失败**  
2. 工具返回一串中文「错误：…」→ 模型继续跑，任务却标成 **`done`**，报告里可能是幻觉数字  

R1 要做成：**软失败不打断图 + 失败可判定 + 按 critical/optional 决定终态**，避免「状态 done、内容是幻觉」。

对应面试深挖题：

> Agent 异常了，是全部失败还是只失败那一部分？你怎么做的？为什么？

---

## 2. 改造前的痛点（为什么要动）

| 层级 | 改造前 | 问题 |
|------|--------|------|
| 工具 | `except` 后 `return "错误：…"` | 有软失败味道，但**无统一协议**，成败靠模型认中文 |
| Runner | 未捕获异常 → `mark_error`；软失败跑完 → **`mark_done`** | 「子 Agent/工具挂了」在状态机上看不出来 |
| TaskStore | 只有 `pending/running/done/error` | 没有「部分成功」 |
| Monitor | 多是「开始调用」 | 看不到失败步骤汇总 |
| Prompt | 仅规范助手写了「勿编造」 | 主流程无 critical/optional 策略 |

**最危险语义**：MySQL 已连不上，模型仍可能写出假周报，任务却是 `done`。

---

## 3. 设计决策（为什么这么做）

### 3.1 工具继续软失败（return 字符串，不抛）

DeepAgents/LangGraph 里工具抛异常可能直接打断图，主 Agent 来不及降级写说明。  
所以业务工具仍 **return 文本**，但改成**带机器可读头**的结构化串。

### 3.2 用 ContextVar 收集失败，而不是只解析主图 astream

子 Agent 内部的 SQL/搜索工具结果，**不会**原样出现在主 Agent 的 `tools` 节点。  
若只在 runner 里解析 chunk，会**漏掉**绝大多数工具失败。

因此：`format_tool_error` 时写入当前协程的 `failure_steps`（ContextVar），任务结束再决策。

### 3.3 critical vs optional

| 角色 | 工具举例 | 失败时任务状态 |
|------|----------|----------------|
| **critical** | 查库、读上传、写 Markdown | `error`（关键路径挂了，禁止假装成功） |
| **optional** | Tavily、RAG、转 PDF | 可 `partial_success`（核心还能做） |

**为什么**：效能周报可以缺「行业实践」一节，但不能缺数据却编造缺陷数。

### 3.4 日志降噪（同轮配套）

同一时期还做了：失败合并为 `failures_summary`、轮询 access 静音、`[Tool]` 默认不 print、连接类 `retryable=false`。  
目的：演示和读日志时不被「同一错误刷 5 行」淹没，**不改变**失败隔离语义。

## 4. 代码做了哪些改造

### 4.1 新增文件

| 文件 | 作用 |
|------|------|
| [`tools/tool_result.py`](../tools/tool_result.py) | `[[EA_TOOL_RESULT]]` 协议；`format_ok/error`；`TOOL_ROLES`；`decide_task_status` |

### 4.2 改造文件

| 文件 | 改了什么 |
|------|----------|
| `tools/db_tools.py` 等全部业务工具 | 成功/失败都走 `format_tool_ok` / `format_tool_error` |
| [`api/task_store.py`](../api/task_store.py) | 新增状态 `partial_success`；记录 `failed_steps` |
| [`agent/mainagent/runner.py`](../agent/mainagent/runner.py) | 结束时读失败列表 → `decide` → `mark_done` / `mark_partial_success` / `mark_error` |
| [`api/monitor.py`](../api/monitor.py) | `failures_summary` / `degraded` / `report_error`；`task_result` 文案改为「等待终态确认」 |
| [`prompt/prompts.yml`](../prompt/prompts.yml) | 主/子 Agent：失败隔离规则；DB 少无效重试 |
| [`api/server.py`](../api/server.py) | 轮询 access log 过滤（降噪） |
| 前端 `App.vue` | 识别 `partial_success`；展示降级 notice；失败步骤说明 |

### 4.3 结构化返回长什么样

```text
[[EA_TOOL_RESULT]]{"ok":false,"tool":"list_sql_tables","role":"critical","error_type":"upstream",...}
查询出现异常：2003 (HY000): Can't connect...
```

- **第一行 JSON**：机器 / Trace / 决策用  
- **后面正文**：给 LLM 读（Prompt 仍可认「错误」「未接入」）

### 4.4 终态决策伪代码

```text
failed = get_failure_steps()
status = decide_task_status(failed)
  无失败           → done
  有 critical      → error      （即使模型已写出长文）
  仅 optional      → partial_success
```

**关键点**：模型 `task_result` 先推送 ≠ 任务成功；终态以决策为准。

## 5. 数据流（建议背这张图）

```text
工具异常/校验失败
    → format_tool_error
        → 返回结构化字符串给 LLM（图继续跑）
        → record_failure_step（ContextVar）
        → （R2）trace_tool_end

主 Agent astream 结束
    → decide_task_status(failed_steps)
    → mark_* + Monitor(failures_summary / error / degraded)
    → 前端：done | 部分成功 | 失败
```

## 7. 面试怎么讲（30 秒版）

> 工具层保持软失败以免打断编排图，但用 `[[EA_TOOL_RESULT]]` 结构化，并写入协程级失败列表——因为子 Agent 嵌套时主图看不到内部工具结果。任务结束按 critical/optional 决策：`error` 或 `partial_success`，避免「工具已失败、任务却 done」。

深挖「为什么不全挂也不全继续」→ 回到第 3.3 节。

| R1 负责 | R2 负责 |
|---------|---------|
| 失败能不能判定、任务终态对不对 | 完整时间线（含成功步骤、耗时）能不能打开看 |
