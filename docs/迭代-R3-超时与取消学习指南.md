# 迭代 R3：分层超时与任务取消

> **学习目标**：能讲清三层超时、`task_timeout_sec` 如何接线、取消后 ContextVar 为何不串台。  
> **挡题**：[Agent 压力面试题](./Agent%20压力面试题完整分类.md) #4 #5  
> **待办入口**：[面试补齐迭代待办.md](./面试补齐迭代待办.md)

---

## 1. 一句话

LLM HTTP 超时早已有；本轮把 **整任务** `task_timeout_sec` 接到 `asyncio.wait_for`，并提供 **取消 API** + `TIMEOUT` / `CANCELLED` 状态。

---

## 2. 改造前痛点

- 配置里有 `task_timeout_sec=600`，但 `create_task` 只 `asyncio.create_task`，任务可无限挂起。
- 前端无法取消；面试问「超时后状态 / Context 清不清」只能空讲设计。

---

## 3. 为什么这么做

| 决策 | 理由 |
|------|------|
| 任务级 `wait_for` | 一处接线即可演示，不必先改每个工具 |
| `TIMEOUT` / `CANCELLED` 独立状态 | 与业务 `error`（critical 工具失败）区分，面试不混淆 |
| runner `finally` reset ContextVar | 取消/超时与成功路径同一清理，防串台 |
| 前端「取消」按钮 | 可 Demo，不只靠 curl |

---

## 4. 改了哪些文件

| 文件 | 改动 |
|------|------|
| [`api/task_store.py`](../api/task_store.py) | `TIMEOUT` / `CANCELLED`；`mark_timeout` / `mark_cancelled` |
| [`api/server.py`](../api/server.py) | `_running_tasks`；`wait_for`；`POST .../cancel` |
| [`api/monitor.py`](../api/monitor.py) | `report_timeout` / `report_cancelled` |
| [`agent/mainagent/runner.py`](../agent/mainagent/runner.py) | `CancelledError` 落 Trace / 状态；finally 仍 reset |
| 前端 `client.js` / `App.vue` | `cancelTask`；超时/取消文案与顶栏按钮 |

---

## 5. 数据流

```text
POST /api/tasks
  → create_task + _running_tasks[id] = Task(_run_task_background)
  → wait_for(run_deep_agent, task_timeout_sec)
       ├─ 正常 → mark_done / partial / error（R1）
       ├─ TimeoutError → mark_timeout + Monitor timeout
       └─ cancel API → Task.cancel() → CancelledError → mark_cancelled
  → finally：pop _running_tasks；runner finally：reset Trace/failure/retry/session
```

## 7. 面试 30 秒

> 三层超时：LLM HTTP（`openai_timeout_sec`）、工具侧可后补、整任务 `task_timeout_sec` 用 `wait_for`。取消走后台 Task 句柄。ContextVar 在 runner `finally` 与成功路径一样 reset，所以超时/取消不会污染下一单。
