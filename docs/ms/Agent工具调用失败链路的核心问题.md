# 这一组问题完整解决方案

> 背景：这是Agent工具调用失败链路的核心问题，全部围绕：**失败不直接抛异常、区分critical/optional、状态由代码控制、杜绝幻觉、重试、超时、partial局部重试**。 答题结构：**现状问题 → 方案设计 → 代码要点 → 面试口述话术**

## 1. 中间某步失败了，怎么继续？谁决定继续？模型还是代码？

### 现状

工具软失败不抛异常；用`critical/optional`标记工具；`decide_task_status`输出`error / partial_success / done`；**继续执行的决策权在任务层代码，不是模型**。

> ❗面试官连环追问重点：**不能让LLM自己决定要不要继续，模型只能输出工具调用，流转逻辑由框架代码控制**。

### 解决方案

1. 工具执行完成，返回结果，附带标记：`is_critical`、`retryable`、工具执行结果、异常信息。

2. 框架调用

   ```
   decide_task_status
   ```

   函数，根据工具类型（critical/optional）+执行结果，计算任务状态：

   - `critical`工具失败 → 任务直接置为`error`，**终止后续所有工具调用**，不再往下跑；
   - `optional`工具失败 → 任务置为`partial_success`，**允许继续执行剩余步骤**；

3. 模型只能输出tool_call，**不能输出“我要继续/我要终止”这类指令**；是否继续完全由任务状态机代码判断。

4. 保存`failed_steps`记录哪些步骤失败。

### 面试口述

> 我们现在采用工具软失败，不直接抛异常中断整个Agent。区分工具是critical还是optional。 critical失败直接标记任务error，停止后续执行；optional失败标记partial_success，可以继续跑剩下步骤。 **是否继续执行由任务层状态机代码决定，不是由大模型来做决策。模型只负责输出工具调用，不能控制任务流转。**

------

## 2. 可选失败后会不会幻觉补数据？如何禁止假数据补齐？

### 现状

Prompt写了禁止补齐，但是只是软约束；**缺少成稿门禁**，`generate_markdown`依然可以生成完整虚假报告。

### 解决方案（两层防护，缺一不可）

1. **第一层：Prompt软约束（辅助）**  提示词明确：工具调用失败，禁止编造、补齐缺失数据，只输出已知信息，错误信息需要明确标注。

2. 第二层：成稿门禁【硬约束，核心】

     在调用

   ```
   generate_markdown
   ```

   生成最终报告之前，校验任务状态：

   - 如果任务状态是`error / partial_success`：**拦截完整markdown成稿输出**；不允许输出完整正式报告；只输出失败摘要、已获取的有效片段，禁止伪造完整报告。

   - 只有状态

     ```
     done
     ```

     ，才允许生成完整正式markdown报告。

     > 注意：模型内部依然可能生成大段文本，但是**不把这份文本返回给前端、不写入存储**。

### 面试口述

> 仅靠Prompt约束是不够的，模型依然会幻觉补齐。我们需要代码层的成稿门禁。 当任务处于partial_success或者error状态时，代码直接拦截完整成稿生成，不输出完整报告，只返回失败摘要。Prompt只能作为辅助手段，不能作为安全保障。

------

## 3. critical失败为何还能写出长Markdown？

### 现状

任务状态已经是`error`，但是模型依然输出一大段markdown正文，前端看到长长的报告，误以为任务成功。**状态和输出内容脱钩**。

### 解决方案

1. 成稿门禁拦截：任务`error`状态，禁止输出完整成稿；

2. 区分：

   任务终态状态 和 返回给用户的正文是两套东西

   。

   - 状态：`error`（框架标记）
   - 返回内容：简短失败说明，**不允许输出完整业务报告**；

3. 可选：即使模型输出了长文本，代码层做过滤，不把完整报告落盘、不返回前端。

### 面试口述

> 现在存在一个问题：任务状态标记为error，但是模型依然可以输出大段markdown。 这里需要成稿门禁做硬拦截：任务失败的时候，禁止生成完整正式报告。 不能依赖模型自己“懂事”，框架要控制输出边界。

------

## 4. 同一工具失败为何还调两次？重试策略是什么？

### 现状

Trace能看到LLM自己发起重试；`retryable=false`没有做代码短路；只靠Prompt禁止重试。

> 坑：LLM自主发起重试，框架无法管控，会出现重复调用同一个工具。

### 解决方案

1. 框架层面做重试控制，

   不要交给模型来决定要不要重试

   - 工具定义字段：`retryable: bool`；
   - 如果`retryable=false`：代码直接短路，**不允许重试，直接记录失败，进入状态机处理**；
   - 如果`retryable=true`：框架做有限次数重试（最大重试次数），重试次数由框架控制，不是模型说了算。

2. Prompt只做辅助：告知模型不要自行发起重试；**但不能依赖Prompt**。

3. Trace记录重试来源：区分「框架主动重试」还是「LLM主动发起的错误重试」，便于排障。

### 面试口述

> 当前我们主要靠Prompt限制模型不要重试，但是不可靠。 理想方案：工具配置retryable字段，由框架代码管控重试。retryable=false直接短路，禁止重试； 如果允许重试，框架控制最大重试次数，而不是让LLM自主发起重复调用。

------

## 5. 工具 / 模型超时怎么做？超时后状态？Context清不清？

### 现状

LLM客户端有超时；`task_timeout_sec`没有接入；没有任务级取消状态。 设计方案：`CANCELLED / TIMEOUT`终态，finally重置ContextVar，当前未实现。

### 解决方案

1. 增加任务级超时配置：`task_timeout_sec`，整个任务有最大执行时间；
2. 增加任务状态枚举：新增`TIMEOUT`、`CANCELLED`；
3. 超时触发时：
   - 标记任务状态为`TIMEOUT`；
   - 取消正在运行的工具调用、模型请求；
   - `finally`块执行：**重置ContextVar上下文变量，清理任务临时上下文，防止上下文污染下一个任务**；
4. 超时属于`critical`类型失败，任务终止，不继续往下执行；
5. 区分：客户端请求超时 vs 整个任务超时。

### 面试口述

> 现在只有客户端层面的请求超时，没有任务级超时控制。 后续设计增加task_timeout_sec任务总超时，增加TIMEOUT、CANCELLED任务终态； 超时后要在finally里重置ContextVar，清理上下文，避免上下文污染后续任务。

------

## 6. partial后能否只重试失败步？

### 现状

目前不支持；只能整体重跑；设计方案：`failed_steps`记录失败步骤，只重跑optional失败的步骤。

### 解决方案

1. 任务执行过程中维护`failed_steps`集合：记录每一步的step_id，标记哪些optional步骤失败；
2. 支持任务恢复：读取`failed_steps`，**只重新执行失败的optional步骤**，已经成功的步骤不再重复执行；
3. 注意：`critical`步骤失败，不能局部重试，任务直接终止；
4. 需要配合checkpointer持久化任务执行快照，保存每一步执行结果，支持断点重跑。

> 约束：只针对optional工具；critical失败不支持局部重试。

### 面试口述

> 当前我们还不支持局部重试。 后续设计维护failed_steps记录失败步骤，对于optional工具失败，可以只重跑失败的步骤，已经成功的步骤不再重复执行。 critical工具失败不支持局部重试，任务直接终止。

# 整套逻辑串联（面试官连环追问完整逻辑）

1. 工具失败不抛异常，区分`critical/optional`；
2. **任务是否继续由代码状态机决定，不是模型**；
3. `critical`失败直接error终止；`optional`失败partial_success继续执行；
4. 重试由框架管控，`retryable=false`直接短路，不靠Prompt；
5. 超时增加任务级超时、TIMEOUT状态，finally清理ContextVar；
6. 用**成稿门禁硬拦截**：error/partial_success禁止输出完整markdown成稿，杜绝幻觉假报告；
7. optional失败可以基于`failed_steps`做局部重试，critical不支持。

# 关键原则（面试一定要反复强调）

1. **Prompt是软约束，只能辅助，不能做安全、边界控制；真正的边界靠代码硬逻辑**。
2. **任务流转、是否继续、重试、输出管控，控制权交给框架代码，不能交给大模型**。
